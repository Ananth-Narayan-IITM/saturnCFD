Detailed Description

Architecture decision records

Every decision that would be expensive to reverse gets a numbered record here before the code that depends on it is written. The goal is control: a decision is visible, argued, dated, and can be superseded without archaeology.

Status values

status meaning
proposed under discussion; do not build on it yet
accepted frozen; code may depend on it
rejected considered and declined; keep the reason
superseded replaced by a later ADR; link both ways

Rules

  1. One decision per record. If a record needs "and", split it.
  2. Record the alternatives, not only the winner.
  3. State the consequence for the code: which module, which interface, which test changes.
  4. An accepted ADR is not edited. Change it by writing a new ADR that supersedes it.
  5. Link the protocol spec and the tests that enforce the decision.

Numbering

0001, 0002, ... in creation order. The template is 0000-template.md.
