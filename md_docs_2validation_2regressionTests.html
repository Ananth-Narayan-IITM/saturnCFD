Regression tests

Status: accepted policy. Tests are added as each module lands.

What a regression test is

A regression test runs a real case through the real binary and compares the result with a stored expectation. It is not a unit test of a helper and not a manufactured-solution order test. It answers one question:

Did a change alter a result that we already accepted?

The expectation is a small text file, not a binary blob, so a diff shows exactly what changed.

Why we need them

Unit tests prove that a function does what its author intended. Manufactured solutions prove the order of accuracy. Neither catches:

  • a change to a boundary condition that shifts a centreline by 2 %;
  • a YAML default that silently changes a case;
  • a mesh reader that drops a patch;
  • a generated template that no longer matches the options the solver reads;
  • an output writer that renames or reorders a field;
  • a linear-solver default that changes the iteration count or the answer;
  • a compiler/backend change that changes the last digits.

A regression test is the memory of the project. It is also the evidence that a fix did not break the validated cases.

What is stored

For every case:

tests/regression/<area>/
<case>.yaml # the exact input
<case>.expected # the accepted result

The .expected file is plain text:

case: traveling64
git: 772d986
date: 2026-10-31
tolerance:
l2: 1.0e-8
linf: 1.0e-7
result:
l2: 0.001234
linf: 0.004567
steps: 3950
maxDivergence: 5.3e-11

Do not store a full field array unless the case is specifically about field output. Store the smallest set of scalars that would catch a real regression.

Rules

  1. Every solver gets a regression case before its first benchmark. Burgers gets traveling64 before any cavity run.
  2. Every bug fix gets a regression case that fails before the fix and passes after it.
  3. Every output-format change gets a regression case for the file header and field names.
  4. Tolerances are explicit and precision-aware. Double and float do not share a tolerance.
  5. A failing regression is never "fixed" by deleting the case. Either fix the code or record the new accepted value with a reason, date and git hash.
  6. Expected files are reviewed. Updating them is a deliberate act, not a test-run side effect.
  7. Case names are camelCase. traveling64.yaml, not traveling-64.yaml.
  8. No dependency on the working directory. Paths come from CMake/CTest.
  9. No hidden nondeterminism. If a case is stochastic or threaded, record the seed and the tolerance.

What to compare

area compare
Burgers \(L^1, L^2, L^\infty\), observed order, shock position, conservation
heat profile at sample points, boundary-layer thickness, \(L^2\)
Stokes Poiseuille/Couette sample values, divergence norm, pressure mean
incompressible cavity centreline RMS/max, steps, max divergence, kinetic energy
mesh checkMesh pass/fail, counts, volume range, structured flag, patch names
config accepted/rejected case, exact error category, generated template round-trip
CLI exit code, report keys, .pvd references
output field names, component count, time/step metadata

Running

ctest --preset regression

or a single case:

saturnCFD tests/regression/burgers/traveling64.yaml

The C++ test harness may also call the library directly for speed. The case file and expected file are still the same.

Updating an expectation

  1. Run the case and inspect the new result.
  2. Confirm the change is intended and understood.
  3. Update the value, git, date and a one-line reason in the .expected file.
  4. Commit the code change and the expectation together.
  5. Mention the change in docs/validation/.

If the change is not understood, it is a bug, not a new baseline.

Why not only unit tests

A unit test of checkMesh can pass while the CLI mishandles -report, or the YAML reader accepts a key the solver never reads. The regression case exercises the path the user actually runs. The unit test tells you where it broke; the regression tells you that it broke.
