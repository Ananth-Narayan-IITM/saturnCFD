# 0010 — Command-line interface and help

- **Status:** accepted
- **Date:** 2026-10-30
- **Owner:** saturnCFD v1
- **Supersedes:** none
- **Protocol:** `docs/protocols/cli.md`
- **Tests:** `tests/cli/...`

## Context

The driver needs a small, memorable interface. The user explicitly asked for
`-checkMesh`, `-report` and `-help`, with each option self-describing. A
positional case-file run remains the common path.

## Decision

Use **single-dash long options in camelCase**:

| option | argument | meaning |
|---|---|---|
| `-help` | optional option name | print general help, or help for one option |
| `-version` | — | print version and build information |
| `-listSolvers` | — | list registered solvers |
| `-checkMesh` | `mesh.msh` | validate a mesh; writes `.vtu` and `.json` by default |
| `-report` | `path` | JSON report path; `.json` is appended if absent |
| `-writeVTK` | `prefix` | also write per-patch `.vtp` and `.pvd` |
| `-checkConfig` | `case.yaml` | validate a case file and exit |
| `-dumpConfig` | `solver\|common` | print the generated YAML template |
| `-writeTemplate` | `file` | write the template; `.yaml` is appended if absent |
| `-mesh` | `mesh.msh` | supply a mesh to `-dumpConfig` for patch names |
| `-threads` | `N` | override the Kokkos thread count |
| `-completion` | `bash\|zsh\|fish` | print a generated completion script |

The positional form `saturnCFD <case.yaml>` runs a case.

Rules:

- Options are case-sensitive and use exactly the spelling above.
- An option that needs an argument consumes the next token.
- `-help` and `-version` take precedence and exit zero.
- An unknown option prints an error, the closest known option and a pointer to
  `-help`, then exits non-zero.
- `-report` is valid only with `-checkMesh` or `-checkConfig`; `.json` is
  appended when absent.
- `-writeVTK` is valid only with `-checkMesh`.
- `-writeTemplate` is valid only with `-dumpConfig`.
- `-mesh` is valid only with `-dumpConfig`.
- `-completion` is a terminal action like `-help` and `-version`.

## Solver template

```bash
saturnCFD -dumpConfig common
saturnCFD -dumpConfig common -writeTemplate common
saturnCFD -dumpConfig common -mesh mesh.msh -writeTemplate common
```

`-dumpConfig` prints to stdout; `-writeTemplate` writes the same content to a
file and appends `.yaml` when the argument has no extension. The template is
generated from the solver's option registration, so it cannot drift from the
code. `common` and `saturnBurger` are registered; a new solver supplies its
schema when it registers. With `-mesh`, the actual patch names are appended as
a comment.

## Mesh visualisation

By default, `-checkMesh` writes `<prefix>.vtu` and `<prefix>.json`, where the
prefix defaults to `results/<mesh-stem>`. `-report results/mesh` sets the prefix
and writes `results/mesh.json`; the `.json` extension is optional.

`-writeVTK output/mesh` additionally writes:

- `output/mesh_<patch>.vtp` — one boundary surface per patch;
- `output/mesh.pvd` — ParaView collection referencing the volume and patches.

The user opens `output/mesh.pvd` in ParaView.

## Completion

`-completion bash|zsh|fish` prints a completion script generated from the same
option list as the parser. The user sources it once:

```bash
source <(saturnCFD -completion bash)
```

Then `saturnCFD -dump<Tab>` completes `-dumpConfig`, and path options complete
files and directories. Directories receive a trailing slash, so
`tests<Tab>` becomes `tests/` and the next `<Tab>` lists its contents.
Completion requires the binary to be on `PATH`; install it with
`cmake --install`.

## Help

```text
saturnCFD -help
saturnCFD -help checkMesh
saturnCFD -help dumpConfig
saturnCFD -help units
saturnCFD -help config
saturnCFD -help mesh
```

General help lists every option, its argument, a one-line description, file
formats, the SI-only rule and examples. Per-topic help explains the option or
topic, its preconditions, the files it reads/writes, an example and related
options. The help text is treated as part of the user interface and is tested.

## Alternatives considered

| alternative | why not chosen |
|---|---|
| GNU-style double-dash long options | the user explicitly asked for `-checkMesh` |
| subcommands (`saturnCFD checkMesh ...`) | more typing and a second parser; the option form is shorter |
| separate `checkMesh` binary | two binaries to build and document; one driver is simpler |
| no per-option help | users have to read the manual; `-help <option>` is cheap |

## Consequences

- **Code:** a small hand-written option parser; no `getopt_long` dependency.
- **Docs:** `docs/protocols/cli.md` is the source of truth for the option list.
- **Testing:** every option has a parser test and a help snapshot.
- **Compatibility:** v1 CLI is not compatible with v0; that is intentional.

## Validation / exit criteria

- `-help` lists all options and exits zero.
- `-help checkMesh` explains `-report` and `-writeVTK`.
- `-help units` states that SI only is accepted.
- `-help dumpConfig` explains `-writeTemplate` and `-mesh`.
- `-checkMesh` on a valid mesh prints PASS and exits zero.
- `-checkMesh` on an invalid mesh prints the error and exits non-zero.
- `-report` without `-checkMesh`/`-checkConfig` is a usage error.
- `-writeTemplate` without `-dumpConfig` is a usage error.
- `-checkMesh` without `-writeVTK` writes `.vtu` and `.json`, but no `.vtp`/`.pvd`.
- `-report results/mesh` writes `results/mesh.json` without a `.json` argument.
- `-writeVTK` additionally produces a `.pvd` that ParaView opens.
- `-completion bash` prints a script containing `-dumpConfig`.
- `-dumpConfig -writeTemplate results/template` writes
  `results/template.yaml` and that file passes `-checkConfig`.
