Scaling of saturnHeat on PARAM Shakthi

This page records the first CPU scaling campaign, including the parts that did not scale well. It is a lab notebook: the numbers are what came out of the cluster, and the interpretation is separate from the claim.

The GPU points were never delivered by the queue, so this page is CPU only. docs/master.md section 8 explains the vocabulary (rank, thread, unit).

What the numbers say

  1. Inside one node the curve is sane. 48 ranks reach 24.3× on 48 cores (51%), and the single 48-thread process is 1.23× faster still (0.208 vs 0.254 s/step). The gap between the two is parallel overhead, not memory bandwidth: same cores, same problem, one has MPI.
  2. Beyond one node it gets worse, not better. 96 ranks is no faster than 48, and 192 and 384 are slower than both. A compute-bound code would keep improving; this is the signature of a communication cost that grows with the number of ranks. The 256³ points show the same shape: 192 ranks (4 nodes) is the best dense point, 384 (8 nodes) is worse.
  3. Weak scaling is poor even on one node. 60% at 8 ranks is not a network effect. 32³ per rank is simply too small: with the two-cell ghost layer a 32³ block is effectively 36³ (+42% cells), and each step does three halo exchanges (one per SSPRK3 stage) of twelve messages.

Cause

  • Work per rank. At 384 ranks each rank owns 5,461 cells. The kernels need roughly 10⁴ cells per rank before the halo exchange amortises, so the last three points are outside the useful range for this mesh.

  • Broken MPI transport on the compute nodes. Every job log carries

    UCP API version is incompatible: required >= 1.17, actual 1.16.0
    (loaded from /lib64/libucp.so.0)

    so OpenMPI 5.0.6 cannot initialise UCX and falls back to a slower path. The collapse exactly at node boundaries (48 → 96 ranks) is consistent with inter-node latency far above the few microseconds the halo exchange expects. This is an environment problem, not a solver problem.

  • Three halo exchanges per step. The SSPRK3 step calls applyBoundaryConditions() after every stage, and each call exchanges all twelve neighbour faces.

What to claim, and what not to

  • Claim the single-node result: 24× on 48 cores, 51% efficiency for 128³, and the 48-thread process marginally faster than 48 ranks.
  • Do not present the 384-rank point as the code's scaling limit; it is a lower bound measured through a broken transport.
  • Do not quote a GPU speedup from this dataset: the GPU jobs never ran.

What to run next

On a single-node machine (lab PC) the transport issue disappears, so the same run gives the honest CPU curve up to the core count, plus one GPU point:

cd HPC/paramsakthi
./tests/runScaling # auto-detects cores and GPUs
./tests/runScaling --weak-n 64 # weak case with 64^3 per rank

--weak-n 64 replaces the 32³-per-rank weak series with 64³ per rank (64³, 128³, 192³, 256³ for 1, 8, 27, 64 units), which is the right size at tens of cores.

If the cluster is used again for multi-node, fix UCX first (load the module that provides UCX ≥ 1.17, or force --mca pml ob1 --mca btl self,vader,openib) and re-run only the ≥96-rank points for comparison.
